# Decisions log

What was chosen and why, per phase. Format: decision — rationale —
alternatives considered. (Kept for interviews and for continuing the
project without assistance.)

## Phase 0 — Setup and foundations (2026-11-03)

### D-001: uv + pyproject.toml + uv.lock (not conda)
README §7 allowed conda/mamba or uv. Chosen: **uv**. Modern wheels cover
the whole core geo stack on Windows and Linux (geopandas reads/writes
through pyogrio with bundled GDAL; shapely 2 and pyarrow ship wheels),
so conda's main historic advantage is gone. uv gives one tool for
Python installs, virtualenv and a cross-platform lockfile, and is much
faster in CI. Risk accepted: if some later dependency truly needs conda,
it gets its own isolated step. Java (for r5py, Phase 4) is installed
separately regardless of this choice.

### D-002: Python pinned to 3.12, `requires-python = ">=3.12"`
`.python-version` pins the project interpreter to 3.12 (the machine
also has 3.14, but the heavy geo/ML wheels are guaranteed mature on
3.12). README said 3.11+; the floor was raised to 3.12 after review:
allowing 3.11 made the lockfile resolve a *second* numpy version for
3.11 environments, under which the bit-exact regeneration test of the
committed sample (see D-006) is not guaranteed. Supported environments
now equal tested environments.

### D-003: ruff format replaces black
README mentioned black + ruff; the working conventions say "ruff and
pre-commit". One tool doing both lint and formatting (ruff ~ black-
compatible style) means one config, one version, no conflicts.
nbstripout kept as planned.

### D-004: dependencies are added per phase
Phase 0 locks only the core (typer, pyyaml, numpy, pandas, geopandas,
shapely, pyproj, pyarrow, h3). Heavy phase-specific packages (osmnx,
rasterio, lightgbm, r5py, pysal, streamlit…) join in their phases. Keeps
CI inside the 2-minute budget and avoids pinning unused packages. h3 is
locked already despite not being imported yet because it is a core
convention of the whole project (H3 v4) and locking it early surfaces
install problems now.

### D-005: CLI commands exist from day one; unimplemented ones exit 2
README "Done when" requires `almaty-access --help` to list all commands
(download…report). But the working rules forbid placeholder TODO
functions. Compromise: every command is registered, validates the
config for real, then exits with code 2 and "arrives in Phase N". No
silent stubs, no broken promise in --help. Two utility commands were
added beyond the README list: `info` (config validation/summary —
debugging aid) and `sample` (regenerates the sample dataset — the
dataset must be reproducible by command, not by hand).

### D-006: Phase 0 sample data is synthetic
The committed sample in `data/sample/` is a deterministic synthetic
stand-in (bbox in central Almaty + 200 seeded points), generated by
`almaty-access sample` from config values. Rationale: Phase 0 has no
download code yet, and tests need *something* real-shaped to exercise
GeoParquet IO, CRS handling and caching offline. Phase 1 extends it
with schema-faithful clips of real layers (one district), as required
by the project conventions. A test asserts the committed files match a
fresh regeneration, so the sample can never silently drift from config.
Known coupling (accepted): that test relies on NumPy's `default_rng`
bit-stream, which NumPy does not promise to keep identical across
*versions* — but numpy is locked in `uv.lock`, so this only surfaces on
a deliberate numpy upgrade, and the test's failure message says exactly
how to refresh (`uv run almaty-access sample`).

### D-007: caching = mtime comparison (make-style)
`needs_rebuild`/`ensure_built` in `io.py` compare `st_mtime_ns` of
output vs inputs. Alternative considered: content hashing (robust to
touch-without-change, but reads every byte of large rasters/matrices).
mtime chosen for O(1) cost; limitation documented in the learning
guide. Missing inputs raise instead of silently rebuilding.

### D-008: MIT licence with neutral copyright line
LICENSE uses "Almaty Jobs & Accessibility Lab contributors" — replace
with your legal name if you prefer. The data licence note lives at the
bottom of LICENSE + in `data/README.md` (code MIT; data per upstream
source; synthetic sample CC0).

### D-009: CI on ubuntu-latest only
Dev machine is Windows, CI is Linux — together they cover both families.
A Windows CI job would roughly double CI time for little extra signal
now; revisit if a Windows-specific failure ever appears.

### D-010: repository/package naming
Python distribution and CLI are `almaty-access`, import package
`almaty_access` (matches README §9). The local folder is `almaty-jobs`;
the GitHub repo name is the user's choice (README suggests
`almaty-jobs-access`) — nothing in the code depends on the folder name.

### D-011: git initialized locally, no commits made
Committing (and creating the GitHub remote) stays with the project
owner, per working rules. `git init` + staged files + installed
pre-commit hooks were prepared so the first commit runs the hooks.

### D-012: fixes from the Phase 0 adversarial review
A 4-lens review (plan conformance, code correctness, tests/CI,
portability) found no critical/major issues and 16 minor ones; these
were fixed:
- `ensure_built(force=True)` no longer bypasses the missing-input check.
- Config validation rejects NaN/infinity (buffer, speeds, bbox), seeds
  above NumPy's 2**32-1 limit, and projected CRSs whose units are not
  metres (e.g. a US state-plane CRS in feet previously passed).
- Config root inference: a config file not inside a `config/` folder
  now roots data paths in its own folder instead of two levels up.
- CLI: config errors exit 1 with a clean message (+ hint when the
  default `config/config.yaml` isn't found because of the working
  directory); the one non-ASCII character in runtime output ("§") was
  removed, since it crashed under legacy Windows code pages (cp866).
- Tests: the `--help` assertion now checks the command list itself (the
  app description already contained the words "access"/"equity"); all 7
  stage guards are parametrized; new tests for the fixes above.
- CI now runs `pre-commit run --all-files` (cached), so the large-file
  guard and nbstripout are enforced server-side, not only via local
  hooks.
Not fixed on purpose: README status line (owner's call, see open
questions); "pytest passes in CI" remains unverifiable until the repo
is pushed to GitHub (D-011); mtime caveat on FAT/exFAT documented
rather than engineered around (D-007 addendum in the learning guide).

### D-013: no empty placeholder modules for Phases 2/5-7
README §9 also lists single-file modules (grid.py, features.py,
equity.py, scenarios.py, viz.py). Only the four sub*packages*
(download/, prepare/, model/, access/) got docstring-only `__init__.py`
files — they organize future modules and document the layout. Empty
single-file modules would be dead code bordering on placeholder stubs
(forbidden by the working rules), so each is created in its own phase.

### Open questions (non-blocking)
- LICENSE copyright line: keep neutral or use your legal name?
- GitHub repo name: `almaty-jobs-access` as in README §9?
- README still says "Status: planning … Code does not exist yet" —
  update that line in the Phase 0 commit or later?

## Phase 1 — Data acquisition and cleaning (2026-11-03)

All five data sources were verified live by a 5-agent research pass
before implementation (URLs fetched, files downloaded and inspected,
APIs called). The findings below cite that pass.

### D-014: the sample dataset is now REAL clipped data
`data/sample/raw/` holds genuine downloads for a ~1.7x2.2 km bbox in
the Almaly core (buildings, POIs, land use, networks, population hexes,
DEM clip, tiny .osm.pbf), produced by `almaty-access sample` via
`config/config.sample.yaml`. Tests and CI only read the committed
files. The Phase 0 synthetic generator (sample.py) was removed — real
raw-format data exercises the actual prepare code, synthetic shapes do
not. District stats in the sample remain synthetic and are labelled
`source=synthetic-for-tests` (real statistics are never fabricated).

### D-015: three OSM access paths, each for what it is best at
osmnx 2.1 for boundary + the three routable graphs (clean simplification,
largest strongly connected component); Geofabrik country PBF (~215 MB,
verified) + pyosmium 4.3 for bulk buildings/POIs/landuse extraction; in
bbox mode (sample) an Overpass XML export converted to a tiny PBF feeds
the SAME extractor. Overpass reliability: the main instance refused
connections during implementation, so the code uses the kumi.systems
mirror for queries and tries overpass-api.de's dedicated /api/map
endpoint first for bbox exports, with a mirror fallback. pyosmium ships
cp312 wheels for Windows and manylinux (verified on PyPI).

### D-016: district statistics are BETTER than the README feared
README §12 listed "district employment stats unavailable" as the top
risk. Research falsified that: the Bureau of National Statistics'
Taldau API serves, per district, (a) employed RESIDENTS (LFS survey,
indicator 702840, annual 2019-2025) and (b) payroll JOBS at the
workplace's district (forms 1-T + 2-MP, indicator 18935544, quarterly
2016-2026Q1) — verified live for all 8 districts. (b) is the correct
Phase 3 training target (jobs located, not commuters), and the contrast
proves it: Almaly has ~250k jobs vs ~132k employed residents; Alatau
~63k jobs vs ~187k residents. Quarterly x multi-year data also means
far more than 8 training rows. `download stats` auto-fetches both into
`district_stats.csv` when absent; an existing file is validated but
NEVER overwritten (it may be manually curated). Enterprise counts by
district (XLSX, 1999-2025) exist as covariates. Usage terms: free with
attribution to the Bureau (stat.gov.kz/ru/description/).

### D-017: district matching is multilingual and case-insensitive
OSM tags Almaty's districts with Kazakh primary names ('Алмалы ауданы',
…, and 'Түрксіб Ауданы' with a capitalization quirk); Russian lives in
name:ru. The boundary download keeps name/name_ru/name_kk and prepare
matches the configured name against all three, casefolded, failing
loudly with the names it actually found. Config keeps Russian names
(the user's working language).

### D-018: population = Kontur KZ release 2023-11-01
Direct public S3 URL (no auth), 14.9 MB gz; layer `population`, columns
h3 (res 8) / population, EPSG:3857 — all verified by downloading and
opening the file. CC BY (attribute Kontur). No newer ready-made H3 r8
product exists (checked Kontur global + GHSL); if fresher data is ever
needed, aggregate GHS-POP R2023A rasters to H3 manually.

### D-019: DEM = Copernicus GLO-30 COGs on AWS (no auth)
Two 1°x1° tiles (N43/E076, N43/E077, ~37+33 MB) cover the study area;
the downloader does a windowed mosaic so only the needed blocks move.
GLO-30 is a surface model (includes buildings/vegetation) — acceptable
for street-slope estimation; heights are meters above EGM2008. The
required attribution text is recorded in data/README.md.

### D-020: no GTFS for Almaty — confirmed, fallback planned
Exhaustive check (Mobility Database catalog, transitland atlas,
open.egov.kz, city portals, 2GIS): no public GTFS exists. Phase 4 will
build the approximate transit network from OSM route relations with
assumed speeds/headways, as README §7 already planned, labelled
"approximate".

### D-021: floor estimation uses tags -> height -> per-function defaults
`building:levels` (or Overture `num_floors`) when present, else
height / 3 m (OSM or Overture height; GHSL height rasters deliberately
skipped for now — optional per README §5.2), else defaults from config
(residential/commercial 2.0, industrial 1.0, public 2.0, unknown 1.0).
Defaults are config so Phase 3's sensitivity analysis can vary them.

### D-022: land use is a polygon layer, not POI points
README §7 listed `landuse=*` among POI tag groups; implemented instead
as a separate `osm_landuse.parquet` polygon layer used by the building
function classifier (and Phase 2 area-share features). Turning area
features into centroid "POIs" would double-count and blur both uses.

### D-023: Overture buildings via the overturemaps package
Release 2026-10-21.0, schema v2.0.0 (attributes: height, num_floors,
subtype, class — verified). Python API `record_batch_reader("building",
bbox=…)`. The buildings theme is ODbL (not CDLA — that is Places), so
the merged building layer carries OSM+Overture ODbL attribution.

### D-024: fixes from the Phase 1 adversarial review
A 4-lens review (conformance, correctness, tests/CI, data quality of the
actual sample outputs) drove these changes, each verified by
re-measuring the sample:
- **POI rules**: pharmacy moved above the health_clinic healthcare
  wildcard (15 of 27 pharmacies had been miscategorized as clinics —
  now 27/27 correct); transit_stop now matches platforms/stations, not
  PTv2 stop_positions, which double-counted stops (188 → 109 ≈ the
  number of physical stops).
- **DSM grades**: node elevations are sampled from a moving-minimum
  filtered GLO-30 (3 px ≈ 80 m) to approximate ground under buildings,
  and the grade cap tightened 0.6 → 0.3. Walk-edge mean |grade| fell
  4.7% → 2.9% (plausible for central Almaty); edges >10% fell
  13.8% → 6.8%. Residual short-edge noise from 27 m pixels accepted
  and documented.
- **Buildings**: non-occupiable structures (roof, construction, bridge,
  ruins, ...) are dropped (~58,000 m² phantom GFA in the sample);
  hangar now maps to industrial.
- **Boundary download**: osmnx ORs tag filters, so the raw layer had
  oblast/village polygons labelled 'district'; now strictly filtered to
  admin_level 6 (and the committed sample boundary was regenerated).
- **Caching honesty**: the config file itself is now a cache input of
  every prepare step, so edits to tunable parameters (IoU, floor
  defaults, buffer) trigger rebuilds instead of silently reusing stale
  outputs.
- **Repo hygiene**: osmnx's ./cache (8 MB of Overpass responses) was
  being committed — now gitignored; two orphaned Phase 0 synthetic
  files removed; check-added-large-files got --enforce-all so the 2 MB
  guard also works on CI's fresh checkout.
- **Synthetic sample stats** now mirror the real Taldau schema exactly
  (same indicator names, month column).
- **Tests**: added offline coverage for the whole download package (the
  PBF extractor runs on the committed sample PBF; Taldau parser on a
  canned payload; the never-overwrite guarantee for district_stats.csv;
  Overpass endpoint rotation; Overture attribute normalization; POI-vote
  tie rules). 104 tests, still ~6 s.
A second correctness pass added four more fixes: slope rasters no longer
fabricate values at DEM-nodata cells (np.gradient computes a finite
central difference AT a NaN cell — now masked); area POIs are placed at
`representative_point()` instead of the centroid (which falls outside
~4% of concave footprints and mis-credits the building-function vote);
`building=manufacture` joins the job-building POI set; and the
completeness table keeps districts with zero buildings (flagged) instead
of silently dropping them.

Known accepted gaps (documented, not fixed): per-district completeness
compares buildings only (Overture Places is an optional §5.2 source —
POI counts shown for context); residual short-edge grade noise above;
rare OSM-internal duplicates (a closed way AND a multipolygon relation
both tagged building=*) are not de-duplicated — a tagging error in OSM
itself, low frequency, revisit in Phase 2 if footprint sums look off.

## Phase 2 - H3 grid and feature engineering (2026-11-03)

### D-025: Grid = hex centroid inside the buffered boundary (intersected with area.bbox when set)
README asks to keep hexes whose centroid is inside the buffered
boundary. For the sample the extra bbox intersection is required: its
raw boundary holds the FULL city polygon (bbox downloads return whole
intersecting polygons), so without it the sample grid would cover the
whole city with data only in the bbox. Districts are assigned by the
largest area overlap in EPSG:32643 with `district_share` stored, so
border hexes are visibly split; buffer-ring hexes get `district = NA`
and `in_city = False`. They stay in the table so k-ring context (and
later accessibility) is not cut off at the city edge; Phase 3 trains on
`in_city` hexes only. The share is clipped to 1.0: a hex fully inside a
district produces ratios like 1.0000000000000002 in float arithmetic.

### D-026: Building mass is split area-weighted; counts stay whole
A building straddling a hex border contributes footprint and GFA to
each hex in proportion to geometric overlap (computed in the metric
CRS); mass outside the grid is genuinely outside and is dropped, not
renormalized back in. Counts, mean/max floors are per-building
(indivisible) and follow the representative point. Alternative
rejected: centroid assignment for everything - at r9 (hex ~0.1 km2) a
large industrial hall can be hex-sized, and putting all of its GFA into
one hex would distort exactly the hexes the job model cares most about.

### D-027: `station` tag added to the POI extraction (column-only); city + sample re-extracted
Phase 2 needs metro stations separately from heavy rail
(`railway=station` + `station=subway`); Phase 1 kept no `station`
column. It is a column-only key (POI_EXTRA_KEYS): a bare `station=*`
without `railway=*` is mapping noise and must not create POIs. The
re-extraction also delivered the representative-point fix for area POIs
city-wide (deferred at Phase 1 close). Interim pois.parquet now carries
`railway`/`station` so the transit block works from the cleaned layer.

### D-028: Near-duplicate pruning on the log1p view, analysis resolution only, with guards
Pairs with |r| > 0.95 on the log-transformed r8 table lose one column;
the same drop list is applied to r9 so both tables keep identical
schemas. Raw heavy-tailed counts make Pearson r meaningless, hence the
log1p view. Two guards, both earned the hard way:
- Small-sample guard: with fewer than 30 cells (MIN_CELLS_FOR_PRUNING)
  pruning is skipped and the report says why - the first sample run
  "pruned" 52 of 87 features because ANY two monotone series through 3
  points correlate near 1.
- Protected set (added after the Phase 2 adversarial review, D-034):
  the first city run dropped README-mandated core features - total GFA
  lost to the building COUNT (r=0.96), and mean elevation lost to
  road distance (r=0.97: a geographic coincidence in a mountain city,
  not a duplicate). PROTECTED_FEATURES (build.py) can never be
  dropped; a high-r pair of protected columns is recorded in the
  report's `high_corr_kept` instead - documented collinearity beats
  silently missing semantics, and the Phase 3 random forest tolerates
  collinear inputs anyway.
Known-by-design drops on the real city: densities (exact multiples of
counts on a fixed-area grid), k-ring means vs sums (disk sizes nearly
constant), and tr_stop_cnt (the same physical count as
poi_cnt_transit_stop). All drops and kept pairs are recorded in
features_report.json.

### D-029: No-NaN gate and explicit fallbacks instead of silent missing values
The build fails if any feature is NaN/inf. Structural zeros are filled
(no buildings -> 0 GFA and 0 floor stats); distance features fall back
to the study-area bbox diagonal when a target class is absent - in the
sample that is net_dist_major_m (no motorway/trunk/primary inside the
bbox -> the constant 2,812 m diagonal; the sample DOES contain 4 metro
stations, so tr_dist_metro_m is real there) - finite, comparable,
documented in the report; hexes missing ANY terrain column borrow that
column from the nearest hex (the slope raster's valid mask is one
gradient-ring smaller than the DEM's, so elevation-only hexes exist in
principle); `pop_per_1k_nonres_gfa` divides by max(non-residential GFA,
100 m2) so hexes without workspace give a large-but-finite ratio.
`cent_dist_subcenter_m` falls back to the centre distance when no
sub-centres exist (the monocentric degenerate case, e.g. the sample).

### D-030: Sub-centres via DBSCAN over business POIs; centre cluster excluded
DBSCAN (eps 400 m, min_samples 40 on the city; scaled down in the
sample config) over office+finance+commercial POIs in EPSG:32643.
DBSCAN needs no cluster count up front and ignores noise - right shape
for an unknown polycentric structure. The cluster nearest the
configured historic centre IS the centre and is excluded; the rest are
ranked by POI count, top 5 kept. The centre itself is config
(`features.center`): Ascension Cathedral in Panfilov Park, the core of
old Verny - editable, and verified visually in the EDA. City result:
5 sub-centres (389/247/147/138/91 business POIs). The largest (389) is
the Otegen Batyr satellite township in the BUFFER, outside the city
boundary: deliberately kept eligible - it is a real job destination
that edge hexes genuinely orient to, exactly what the buffer exists
for - and labelled with an `in_city` column in subcenters.parquet so
maps and Phase 3 can tell satellite clusters from Almaty's own
sub-centres (Barakholka corridor, Almaty-1 station area).

### D-031: Betweenness centrality: sampled (k=500), seeded, on the full buffered drive graph
Exact betweenness is O(V*E) (~2.8e9 here) for no analytical gain;
Brandes sampling with k=500 sources (config, capped at n, seeded from
random_seed) approximates it in ~2 min on 33k nodes. Undirected simple
graph with min length over parallel edges - through-movement potential,
not routing. Computed once on the full buffered network so values near
the city edge are not biased by a cut graph, then aggregated per hex
(mean and max) at both resolutions.

### D-032: Deliberate deferrals
Routes-per-hex (README transit examples) needs OSM route relations;
Phase 4 extracts them anyway for its no-GTFS fallback, so the feature
arrives there instead of being half-built now. The same applies to the
README's "distance to nearest metro / BRT stop": the metro half ships
now (station=subway), while identifying BRT-corridor stops also needs
route relations, so the BRT half arrives with Phase 4. Night lights
are marked optional in the README - skipped. Land use is read from the
raw layer (clip+group on the fly) instead of adding a prepare step: it
is a single cheap consumer; revisit if a second consumer appears.

### D-033: New dependencies: scikit-learn, networkx (explicit)
scikit-learn for DBSCAN now and the Phase 3 random forest; networkx
was already a transitive osmnx dependency but is now a direct one
because feature code imports it. Both mainstream, wheels everywhere.

### D-034: Adversarial review round (4 lenses + verification) - all 4 confirmed majors fixed
Four reviewer agents (plan conformance, spatial-math correctness,
tests/CI, data quality of the actual parquet outputs) + one
adversarial verifier per major claim. Every major was CONFIRMED with a
reproduction and fixed:
- **Two-way streets double-counted in road lengths.** The interim
  layers store osmnx DIRECTED edges (u->v AND v->u share one
  geometry); summing rows inflated net_len_* by 1.21x (major roads) to
  1.98x (local streets) - enough to distort the class mix 1.6x. Fix:
  `undirected_edges()` keeps one row per (node pair, key, length) for
  length features; keeping length in the key spares genuine dual
  carriageways (~0.2% of pairs). Degrees and betweenness already
  collapsed direction - the inconsistency is what gave it away.
- **Greedy pruning removed README-mandated features** (total GFA lost
  to building count; mean elevation lost to a coincidental r=0.97 with
  road distance). Fix: PROTECTED_FEATURES (see D-028 update).
- **`net_len_service_m` was structurally zero**: osmnx
  network_type='drive' never downloads highway=service/track, so the
  class could not receive a metre. Dead feature removed from
  HIGHWAY_GROUPS/GROUP_ORDER (schema: 86 features before pruning).
- **`building=no` leaked phantom GFA** (a Phase 1 gap): OSM's explicit
  not-a-building marker was missing from NON_OCCUPIABLE_TAGS, so the
  Almaty TV tower (height 371.5 m / 3 m per level = "124 floors")
  shipped as 60,127 m2 of public floor space on Kok-Tobe, plus two
  more objects - 111,870 m2 of fabricated GFA total. Fixed in prepare
  + a warning for height-derived floor counts above 55.
Minors fixed in the same round: land-use groups made mutually
exclusive via precedence (industrial > commercial > green >
residential; blanket residential polygons had pushed per-hex share
sums to 1.95 over industrial zones); log1p prefixes narrowed so
shares/floor-stats/ratios are not log-transformed; terrain borrowing
keyed on any missing column, filling only the gap; self-loops no
longer count as street neighbours; sub-centres labelled `in_city`;
the fallback-distance and pruning paths got direct unit tests; a CLI
test made cwd-independent; and this file plus the learning guide were
corrected where their pruning narrative contradicted the shipped
report (the original text blamed a pop-vs-residential-GFA drop that
never happened; the real pair was pop_residents vs bf_bldg_cnt,
r=0.97, now a protected kept-pair).

Open questions for the user (Phase 2):
- The historic centre is set to the Ascension Cathedral / Panfilov Park
  area (43.2586 N, 76.9532 E). If you would rather anchor on Republic
  Square or Abay/Dostyk, change `features.center` and re-run
  `almaty-access features --force`.
- `features.subcenters` (eps 400 m / min 40 POIs / top 5) found five
  plausible sub-centres; tune and re-run if your local knowledge
  disagrees with the EDA map.

## Phase 3 - Job-density model (2026-11-04)

### D-035: Target = payroll_jobs_located, annual means, district-year panel
The model disaggregates jobs AT the workplace, so the target is Taldau
indicator 18935544 (payroll jobs located in the district), never
employed_residents (counted at home; the difference is commuting -
see the Phase 1 two-definitions note). Quarterly values are averaged
per year to smooth seasonality; training uses 2021-2025 x 8 districts
(40 rows). Honesty note: features are static 2026 OSM, so extra years
do NOT add independent feature-target pairs - they stabilise each
district's target. Validation therefore holds out whole districts
(all their years), never single rows. resolve_years() intersects the
configured years with what the CSV actually holds and falls back
loudly (the synthetic sample has one year).

### D-036: One unit system for training and prediction
The forest trains on district rows and predicts on hex rows, so
model/aggregate.py converts every mass feature (m2, counts, metres,
persons, k-ring sums) to a density per km2 at BOTH levels, and
aggregates intensities (shares, means, distances, entropy, ratios) as
means. A feature column matching no rule raises - a future feature
cannot silently enter the model in the wrong units. The configured
log1p transform is applied after densitisation, identically on both
sides.

### D-037: Model A coefficients are relative weights, not estimates
jobs per 100 m2 GFA: commercial 3.0, public 2.5, industrial 1.0,
unknown 0.5, residential 0.1 (config). Because every district is
rescaled to its official total, only the RATIOS shape the surface;
the notebook's sensitivity check (commercial x0.5 / x2) confirms hex
rankings barely move. A district whose weights sum to zero still
holds official jobs: they are split equally over its hexes, loudly.

### D-038: Model B: fixed hyperparameters, per-tree uncertainty, exact central conservation
RandomForest(n=500, min_samples_leaf=2, max_features=0.5, seeded) on
log(jobs/km2). Hyperparameters are set once from common practice and
NOT tuned against LODO - with 8 districts, tuning the validator is
self-deception. Each tree yields a surface; each is rescaled per
district (strictly positive weights, so no zero-sum guard needed);
P10/P90 are per-hex quantiles across the 500 rescaled surfaces, and
the central estimate rescales the median surface once more so
jobs_rf conserves district totals EXACTLY (the quantile bands
conserve only approximately - recorded in the module docstring).

### D-039: The LODO verdict, reported honestly
Model B beats Model A on MAPE 34.1% vs 60.5% (README done-when: met -
MAPE is the right headline metric when districts span 29k-255k jobs,
and B roughly halves the error on the small dormitory districts
where A's GFA heuristic badly overshoots). Model A keeps the lower
MAE (46.5k vs 53.5k) and the only positive R2 (0.48 vs -0.04): the
forest underpredicts held-out Almaly (75k vs 252k actual) because
trees cannot extrapolate - with the densest district held out,
nothing in training looks like it. Decision: accept and document
rather than tune away; the production surface never uses predicted

## Phase 4 - Travel times and accessibility (2026-11-04)

### D-044: Transit from OSM route relations - approximate, and a lower bound
No public GTFS exists for Almaty (D-016), so the README fallback applies:
`route=bus|trolleybus|subway` relations from the already-downloaded PBF.
What the data actually holds (country-wide): 293 such relations, of which
only 100 carry usable ordered stop/platform node members; 193 are
route-ways-only and CANNOT yield stop-to-stop legs - they are excluded
and counted in `transit_extract.json`. Inside the buffered city: **55
routes kept (48 bus, 5 trolleybus, 2 subway = both directions of the one
metro line), 291 stops, 396 legs**. Validation: the kept subway
relations have exactly 11 stops per direction and ~13 km of legs - the
real line has 11 stations over 13.4 km. Two consequences, stated
everywhere the numbers appear: (1) transit times are APPROXIMATE
(assumed speeds/headways, D-047); (2) coverage is a LOWER BOUND - only
127 of 1,846 r8 hexes host a mapped stop, so hexes served by real buses
whose OSM relations lack stop members fall back to walking.
**Open question for the user:** synthesizing stops every ~350 m along
the 193 ways-only relations would lift coverage at the cost of inventing
stop locations; real AlA stop/headway data would be better. Decide
before Phase 5 reads the transit layer as "access deserts".

Member-list rule: PTv2 tags each halt as a `stop` (position on the way)
and/or `platform` (where passengers wait). Relations are used with
whichever list is LONGER - one Almaty route maps 56 platforms but only
13 stop positions, so "prefer stops" (the first implementation) threw
away three quarters of its sequence. Lists are never mixed: a relation
listing both would traverse every halt twice. Sequences break at any
stop that is outside the area or unlocated (a leg must not bridge the
gap), consecutive stops < 40 m apart are one halt mapped twice, and a
> 20 km leg is treated as a data error (break, counted).

### D-045: Resolution policy - walk at r8+r9, bike/transit/car at r8
Walking is the fine-grained mode (r9 ~ 350 m hexes, 1.89M pairs within
60 min); bike/transit/car matrices at r9 would multiply storage by ~50
while adding nothing the r8 surface does not show at their spatial
scale. Services (nearest, 2SFCA) are walk-based and live at both
resolutions.

### D-046: Speeds - Tobler walk, linear bike, free-flow car, per-mode circuity
- **Walk:** Tobler's hiking function W(s) = 6·exp(-3.5·|s+0.05|) km/h on
  the DIRECTED edge grade from Phase 1, rescaled so flat ground equals
  the configured 4.8 km/h (the classic constant gives 5.04). Uphill and
  downhill differ per direction - this is why the walk graph keeps both
  directions of every street.
- **Bike:** transparent assumption (constants in `access/speed.py`):
  -1 km/h per 1% climb, +0.5 km/h per 1% descent, capped at 1.4x flat,
  floored at 0.25x flat (pushing pace). No claim of a fitted model.
- **Car:** free-flow speed by OSM highway class from config
  (`*_link` ramps map to their base class, unlisted classes use
  `default`). Reference mode only; congestion is deliberately absent,
  so car access is an upper bound and is labelled so.
- **Circuity is per mode** (bus/trolleybus 1.3, subway 1.05): legs use
  straight-line stop-to-stop distance x circuity. The first
  implementation used 1.3 for everything and inflated metro end-to-end
  times by ~30% - tunnels do not wind through the street grid. With
  1.05 the modeled metro end-to-end is ~26 min in-vehicle, consistent
  with the real ~22-25 min given the assumed 32 km/h commercial speed.

### D-047: Headway-based transit graph (no timetable)
The frequency-based standard: each (route, stop) gets a virtual node;
boarding costs half the route's headway (expected wait of a random
arrival at uniform headways), riding costs leg distance x circuity /
assumed commercial speed (dwell included in the speed), alighting ~1 s.
The walk network is part of the same graph, so Dijkstra finds access,
egress and transfer walks itself, and every extra boarding pays a new
expected wait - exactly what a transfer costs in a frequency-based
world. Headways come from the relation's `interval` tag when parseable,
else from config assumptions (bus 10 / trolleybus 12 / subway 7 min) -
and the tag is RARE: only **2 of the 55 kept routes** carry one (both
16 min); the other 53 run on the assumptions. (Country-wide, 8 of the
100 extracted relations have parseable tags; `transit_extract.json`
reports both scopes separately.) Assumed commercial speeds: bus 17 /
trolleybus 15 / subway 32 km/h. `travel.departure_window` stays
reserved for a future timetable-based (GTFS/r5py) path: the headway
model has no departure times - the peak enters only through the assumed
headways - so the window is deliberately unused and its config comment
says so. **All assumptions sit in `access.transit` in
config.yaml precisely so someone with real operational data - the
project author works at Almaty's traffic management centre - can refine
them without touching code.** Implementation trap recorded: a
zero-weight edge in a scipy sparse graph is indistinguishable from "no
edge", so alight/connector arcs are floored at 1 second.

### D-048: Snapping - largest strongly connected component, capped at 2 km
Hex centroids snap to the nearest node of the mode graph's largest
strongly connected component (snapping onto a disconnected service loop
would fake city-wide unreachability), and the straight-line snap
distance is walked at flat speed and added to every time through that
hex (README 4.2). Hexes snapping farther than `access.snap_max_m`
(2 km) are off-network: excluded from matrices and counted per mode in
the report (city r8: 26 walk / 32 bike / 444 car hexes - mountain and
steppe cells; raw car snap p95 is 9.4 km). Caveat this creates: a pair
of kept mountain hexes can owe most of its "car" time to the walk to
the road - a routing app silently moves the pin to the road instead,
so spot checks there look odd but are not wrong.
**Intrazonal rule** (review round): a self-pair (origin = destination)
costs ONE snap leg, not two - a traveller already inside the hex never
walks out to the network and back. Before this rule, 84 in-city r8
hexes "could not reach their own hex" within 15 minutes (double-snap
up to 48 min); the affected hexes carry 0.7% of jobs and 0.03% of
residents, but the artifact was embarrassing and the one-leg rule is
the defensible reading.

### D-050: Matrices - batched scipy Dijkstra, long format, <= 60 min
As the README prescribes: graphs become CSR matrices (seconds), origins
run through `scipy.sparse.csgraph.dijkstra` in batches of 512 with
`limit = max threshold`, results are stored long (`origin_h3, dest_h3,
minutes`) keeping only pairs within 60 min. City scale: walk r9 =
1,891,915 pairs from 12,710 snapped origins (175 of the 12,885 r9
hexes are off-network, D-048) in ~12 s; car r8 = 1.70M pairs
(free-flow reaches almost everything). Nearest-facility times avoid a
per-facility loop entirely: one Dijkstra from a virtual super-source on
the TRANSPOSED graph, with source-to-facility arc weights equal to each
facility's own snap walk - exact min over facilities in a single pass.
The COO-sums-duplicates trap is regression-tested at all four places
it bites: parallel street edges keep the fastest time, repeated route
legs keep the fastest hop, two facilities on one node keep the smaller
snap arc, and a forced two-batch Dijkstra run must match the
single-batch run exactly.

### D-054: Inequality measures - exact on the piecewise-linear Lorenz curve
Every resident of a hex is assigned the hex's accessibility; hexes are
weighted by residents. Sorting residents from worst to best served and
accumulating people and access gives a Lorenz curve that is exactly
piecewise linear (one vertex per hex), so Gini (twice the area to the
diagonal) and Palma (access share of the best-served 10% over the
worst-served 40%, read off the same curve) are exact, not grid
approximations. Weighted quantiles are the inverse weighted CDF,
compared on raw cumulative weights with a relative tolerance (five
weights of 0.3 at the 20th percentile: 0.2 x 1.5 evaluates to
0.30000000000000004, a hair above the first cumulative weight 0.3, and
without the tolerance the answer skips the first hex). Tests pin the
definitions three ways: hand-computed cases, the equivalence "a hex of
w residents = w one-resident hexes", and the textbook
mean-absolute-difference formula. Only BENEFIT measures (acc_, accpct_,
sfca_) get these statistics; minutes-to-nearest run the other way and
get share-of-residents-within-T tables, where a missing time
(off-network, unreachable) counts as beyond every threshold rather than
dropping the worst-served from the denominator.
Results at r8, raster -> calibrated weights (D-058): Gini 0.005 -> 0.004
car / 0.25 -> 0.23 bike / 0.62 -> 0.59 transit / 0.63 -> 0.60 walk;
Palma (raster) 0.25 / 0.76 / 8.0 / 8.7. Free-flow car access is almost
perfectly equal; walking and (approximate) transit access are held by
few.

### D-055: Desert rule - dense hexes among the worst-served quarter of residents
README: "population above the 75th percentile and accessibility below
the 25th percentile". Read literally (both percentiles across hexes) the
rule flags almost nothing for the headline job measures: 0, 0, 0 and 1
of 712 r8 hexes (transit, car, bike, walk) and, for walking at r9, 10
of 3,329 (12 with calibrated residents). The access percentile across
hexes is set by the many near-empty outskirt cells, far below anything
a dense hex experiences. (It is not empty in general - the 15-minute
walk and transit measures flag 22 r8 hexes each - so this is a property
of these measures, not a theorem.) Adopted reading:
population above the 75th percentile across hexes (density is a
property of the hex) AND access at or below the population-WEIGHTED
25th percentile (the level under which the worst-served quarter of
residents live). The literal count ships beside every result
(`n_hexes_literal_rule`), computed with the SAME `<=` comparison so the
two differ only through the weighting of the quantile; for
zero-inflated 2SFCA both thresholds are 0 and the two rules coincide,
and `pop_share_at_or_below_access_threshold` says how many residents
share the bottom value (52% for kindergartens, 45% calibrated) instead
of pretending it is a clean quarter. A measure with no meaningful low
tail reports no deserts at all: free-flow car, where the worst-served
quarter still reaches on average 98.5% of what the median resident
reaches (`low_spread`, threshold 0.95) - a relative rule would
otherwise flag a tenth of residents for nothing. The guard compares
the MEAN of the worst-served quarter, not its upper edge: when a
quarter of residents share the median value, the edge equals the
median whatever lies below it (D-064).
**The list depends on the population weighting** (both halves of the
rule use residents). Transit 45 min at r8: 24 hexes / 145,841 residents
(9.6%; Alatau 103,968) on the raster, 33 hexes / 164,802 (10.8%)
calibrated; 21 hexes are deserts under both, and the top-ranked hex
differs. Both lists are in `equity_deserts.parquet`; the notebook maps
the common core separately. And these are mostly not transit findings:
only 1 of the 24 has a modelled route while 19 contain mapped stop POIs
(calibrated: 1 of 33, and 24), so their "transit" access is a walking
value (D-063).

### D-056: LISA with PySAL - and tie-aware p-values, because the library's break
Engine: esda 2.10 / libpysal 4.15 (the PySAL the README names; joined
in its phase per the Phase 0 dependency policy; numba is NOT needed -
LISA over the 3,329 r9 hexes takes 1.3 s at 999 permutations and 3.8 s
at 9,999, over the 712 r8 hexes 0.3 s and 0.9 s). Weights: H3 ring-1
neighbours that are also inhabited, row-standardized; a hex with no
inhabited neighbour is an island and can never cluster. Global Moran's
I is 0.84-0.99 for the job measures - by construction (neighbours
share most of what they can reach) - so only the LOCAL statistic
informs.
Fewer than 20 inhabited hexes -> LISA skipped with a recorded reason
(the 3-hex sample at r8; the sample's r9 exercises the full path).

**P-values are computed here, from esda's own seeded conditional
permutations, because every variant esda offers fails on this data** -
accessibility measures are zero-inflated (67% of inhabited r9 hexes
have a kindergarten 2SFCA of zero), and zeros tie:
- esda's recommended `alternative="two-sided"` mirrors the observed
  percentile into the opposite tail and counts everything beyond it;
  the mass of tied all-zero neighbourhoods lands inside that count.
  Observed on kindergartens: no p-value below 0.084 at 999 permutations
  (0.090 at 9,999), hence not one significant cell for a variable whose
  global I is 0.77.
- esda's one-sided tails compare floats with `>=`. The observed
  statistic of a zero hex among zero neighbours and the permutations
  that tie with it differ in the last bits, so the ties go uncounted:
  a zero hex with two zero neighbours gets p = 0.001 at 999
  permutations although a third of them tie with it (tie-inclusive
  one-sided tail 0.33). Observed on schools: 1,446 zero-region "cold
  spots".
- esda's third option, `folded`, falls into neither trap, but it folds
  the reference distribution about its mean - and that distribution is
  skewed, so one tail becomes unreachable: 397 walking hot spots and
  not one cold spot (999 permutations).
`tie_aware_p` counts both tails with a float tolerance and doubles the
smaller one (the textbook conservative two-sided permutation p-value).
On the tie-free walk measure it agrees with esda's two-sided result to
within a few hexes (340 HH / 781 LL vs 343 / 800 at 999 permutations;
341 / 803 vs 341 / 809 at 9,999); on zero-inflated measures it finds
provision hot spots and - correctly - no cold spots: a zero among zeros
is not surprising when most hexes are zero. A regression test plants
both traps. The project's own Phase 2 Moran's I and esda's agree to 4
decimals on the same weights.

Multiple testing: one test per hex. The report carries the count that
survives Benjamini-Hochberg control at the same alpha, split into hot
and cold. That needs p-value resolution: the smallest two-sided p is
2/(permutations+1), and BH over m tests admits floor-level cells only
when at least ceil(floor * m / alpha) of them exist - 133 at 999
permutations over the 3,324 r9 tests, 14 at the city's 9,999 (sample:
999). Where even that is not met and nothing passes, the count is
reported as NULL ("unresolved"), not as zero: schools (8 floor-level
cells on the raster, 3 calibrated) and clinics (4) at r9.

**Cluster counts are Monte Carlo estimates.** A pseudo p-value doubles
a tail share counted over a finite number of permutations; at 9,999
its standard error near 0.05 is about 0.003. The report therefore
carries, per measure, the hexes within two standard errors of alpha
(`borderline`): significant ones another seed could drop, and
non-significant ones it could add. A one-off check with four seeds at
9,999 permutations (a scratch measurement, not a pipeline output) shows
what the field means:

| measure | HH / LL in the report | borderline | HH across 4 seeds | LL across 4 seeds |
|---|---|---|---|---|
| transit 45, r8 | 78 / 157 | -9 / +4 | 78 in every run | 154-159 |
| walk 30, r9 | 341 / 803 | -36 / +29 | 335-345 | 784-803 |
| schools 2SFCA | 168 / 0 | -20 / +23 | 162-183 | 0 |
| kindergartens 2SFCA | 240 / 0 | -15 / +9 | 230-240 | 0 |
| clinics 2SFCA | 219 / 0 | -122 / +61 | 219-279 | 0 |

Job measures are stable to a few percent. The zero-heavy 2SFCA
measures are not, because their reference distribution is lumpy.
Clinic 2SFCA is 62% zeros plus 13 extreme hexes (above 10 per 1,000
residents, up to 35: a facility next to almost no residents), and a
shuffled neighbourhood beats an ordinary hot one essentially only when
it draws one of those 13 - about 2.4% of shuffles. Every hex whose
neighbour mean lies between 1.4 and 1.9 therefore gets the SAME
p-value (56 hexes at exactly p = 0.0486), and such blocks cross the
0.05 line together. Read those counts as rough, and the FDR-surviving
ones as the firmer part (kindergartens: 100 in the report, 80-100
across the four seeds).

Results (r8, transit 45 min): I = 0.90; 78 HH and 157 LL hexes, of
which 134 survive FDR (63 hot, 71 cold; 125-151 across the four
seeds). The cold spots lie in outer Alatau, Nauryzbay, the Medeu
foothills and north-east Turksib. For job measures the cluster
LOCATIONS do not depend on the population weighting (the statistic is
computed on hex values, which contain no residents - a test compares
the two per-hex files label by label); the resident shares do: cold
spots hold 2.1% of residents on the raster and 1.9% calibrated (0.8%
and 0.7% in FDR-surviving cold spots), the central hot spot 24% and
34%. Large in area, thin in people. 2SFCA values DO depend on the
weighting (D-058), and so do its hot spots: schools 168 raster / 130
calibrated with 93 in common, kindergartens 240 / 182 (149), clinics
219 / 231 (170). Those differences are of the same order as the
seed-to-seed variation above: that the hot spots move is established
(the values changed), by how many hexes is not.

### D-057: Mode gap = transit / car, a lower bound over an upper bound
`modegap_transit_car_T` divides jobs reachable by approximate transit
(a lower bound, D-044) by jobs reachable by free-flow car (an upper

is reported as a ranking, not a finding: median ratio 0.037 at 45 min
(0.048 calibrated), 87% (82%) of residents below 0.25 ("the car reaches
over four times as many"). At 15 minutes the modelled transit adds
nothing over walking for any resident, so that column is a walk/car
ratio - the report says so per threshold
(`pop_share_transit_equals_walk`).

### D-065: A scenario is a GeoJSON data file, not code

**Decision.** README §7 Phase 6 says "define a scenario as a GeoJSON",
and the implementation takes that literally: one FeatureCollection per
scenario in `config/scenarios/` (file stem = scenario name), features
discriminated by a `kind` property — `line` (a transit line,
LineString), `stop` (an explicit station of a named line, Point),
`bike_boost` (a street corridor with a higher flat bike speed,
LineString). Everything an operator might tune — mode, speed, headway,
stop spacing, corridor width — is a feature property with defaults from
config; provenance (title, note, source links) travels in the file's
top-level `properties`, and the report echoes it. The alternative
(scenarios as Python code or config fragments) was rejected: the whole
point of the phase is that redrawing an alignment must not require
touching the pipeline.

Semantics that needed deciding, and why:

- **An extension rides the same train.** A `line` with
  `extends_route_ref` attaches its legs to every existing route of that
  mode and ref whose first or last stop lies within
  `scenarios.attach_max_m` of one of the drawn line's ends — appended
  after a route that ends there, prepended before a route that starts
  there, which extends a two-relation service (one relation per
  direction, like the metro) in both directions. Modelling the
  extension as its own route would charge riders a phantom second
  boarding wait (half the headway, 3.5 min for the metro) at the old
  terminus; a unit test holds the difference between the two modelling
  choices to exactly that wait. Speed/headway overrides are forbidden
  on extensions — same trains, same schedule.
- **Drawn length is exact, so circuity must not inflate it.** Baseline
  legs store straight-line stop-to-stop distances because OSM relations
  carry no usable path geometry; the graph build multiplies them by a
  per-mode circuity factor (D-046). A scenario line's length is
  measured ALONG the drawn alignment — it IS the path — so new lines
  ride under their own mode key (`line:<name>`) with circuity 1.0 and
  their own speed, while extension legs (which must keep the extended
  route's mode) are stored pre-divided by that mode's circuity so the
  multiplication restores the drawn length. Merged tables live only in
  memory; nothing on disk carries an adjusted distance.
- **One route, both directions.** A new line's legs run both ways under
  one route id: each (route, stop) pair has one virtual node, so
  boarding pays the expected wait once and may ride either way —
  exactly what two per-direction relations would charge.
- **Stations order themselves along the line.** Explicit stops are
  sorted by their projection onto the alignment (feature order is
  irrelevant), must lie within 200 m of it, and a station within 50 m
  of the stop an extension attaches at is that terminus redrawn — it is
  merged away, and hop lengths are measured from the terminal's
  projection onto the line, not from the drawn duplicate. A line
  without drawn stops synthesizes stations every `stop_spacing_m`
  (BRT-style regular spacing).
- **Bike corridors match edges by overlap, not intersection.** An edge
  belongs to a corridor when at least half its length lies inside the
  drawn line's buffer (`bike_buffer_m`); plain intersection would catch
  every side street crossing the corridor. Matched edges get the
  boosted FLAT speed with the grade handling unchanged (a protected
  lane does not flatten a hill) and are never slowed below baseline.
- Validation is strict (unknown kinds, unknown property names, far-away
  stops, out-of-range speeds all fail naming the file and feature): a
  drawing typo should die at load, not surface as a silent zero-delta
  scenario.

### D-066: Scenarios rebuild only the affected mode — and must reproduce the baseline exactly

**Decision.** `almaty-access scenarios` (Phase 6) never recomputes the
baseline: it reads the stored `access_r8.parquet` as "before", merges
each scenario into the baseline transit tables (or boosts bike edges),
rebuilds that one mode's graph, runs the same batched-Dijkstra
`hex_times` and the same `cumulative`/`gravity` measure code as Phase 4
(same rounding, share computed from unrounded counts), and stores
per-hex `{column}_base/_scen/_delta` at the analysis resolution.
Matrices stay in memory — three scenario runs on the full city take
seconds and write no multi-million-row files.

The guarantee that makes the deltas trustworthy: running the scenario
code path with NOTHING drawn reproduces the stored Phase 4 transit
matrix BIT FOR BIT (a pipeline test asserts exact frame equality, and
the per-hex `_base` columns are asserted equal to the access table).
And because a scenario only ADDS arcs to a graph (or speeds edges up)
and the rounding is monotone, every delta is provably >= 0 — the build
raises if it ever sees a negative one, turning the monotonicity
argument into a permanent bug detector. Scenario stop/route ids start
at 10^12 (`SCENARIO_ID_BASE`), two orders of magnitude above current
OSM ids, so merged tables cannot collide with real ids.

Caching: one `ensure_built` over all scenario outputs, with every
scenario file among the inputs; a renamed or deleted scenario's per-hex
file is an orphan and is removed on the next build (same pattern as the
equity stage's calibrated orphans).

### D-067: Scenario equity under both weightings, on the Phase 5 domain

**Decision.** The README's Phase 6 outputs — "population gaining > X
jobs" and "change in Gini" — are produced under BOTH Phase 5 population
weightings (D-058): the Kontur raster as prepared, and the raster with
district totals rescaled to the employed-resident shares. The
calibration factors are derived on the same inhabited domain (in-city,
raster residents >= `equity.min_population`) with the same
`calibrated_weights`/`apply_factors` recipe the equity stage uses, so a
scenario's Gini-before equals the equity report's Gini for the same

trusting the claim. Gains count residents of hexes whose

and threshold T come from the first `accpct_jobs_{mode}_<T>` entry of

### D-072: Streamlit, pydeck and Altair are regular dependencies

**Decision.** The three app libraries go into `[project.dependencies]`
(streamlit>=1.60 — the `width="stretch"` API replacing the deprecated
`use_container_width` — pydeck>=0.9.1, altair>=5.4), not an optional
extra. Streamlit Community Cloud installs the package straight from
`pyproject.toml`, and an extra would have to be spelled in a separate
requirements file there; the pipeline never imports any of them, so the
only cost is install weight for pipeline-only users. The app theme
(`.streamlit/config.toml`) carries the chart-system surface/ink/blue so
Streamlit chrome matches the figures; the static web map is pydeck's
standalone HTML with a title/legend/caveat overlay injected before
`</body>` (pydeck has no overlay API) and the key-less Carto basemap.
